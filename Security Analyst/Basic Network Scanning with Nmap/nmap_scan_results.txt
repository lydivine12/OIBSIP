SECTION 4: OPEN PORTS — SERVICE EXPLANATIONS AND SECURITY RISK ANALYSIS
--------------------------------------------------------------------------------

PORT 22/tcp — SSH (OpenSSH 9.6p1, Ubuntu build)
--------------------------------------------------------------------------------
What it does:
  SSH (Secure Shell) provides encrypted remote command-line access to a
  machine. It's the standard way system administrators log into Linux
  servers remotely, and also underpins secure file transfer (SFTP/SCP) and
  tunnelling.

Security risk assessment: LOW-TO-MEDIUM (depends heavily on configuration)
  - SSH itself is a mature, well-audited protocol and is *not* inherently
    risky to expose — it's designed to be internet-facing.
  - However, it is one of the single most commonly brute-forced services on
    the internet. Automated bots constantly scan for port 22 and attempt
    credential-stuffing / password-guessing attacks against it.
  - The specific risk level depends on configuration choices, not the mere
    fact that the port is open:
      * Is password authentication enabled, or only key-based auth?
        (password auth is far more brute-forceable)
      * Is root login permitted directly (`PermitRootLogin`)? This should
        normally be disabled.
      * Is the OpenSSH version current? (9.6p1 here is a recent release with
        no widely known unpatched critical CVEs at time of writing — but
        this should always be checked against the current CVE database
        before relying on it).
      * Is it rate-limited / protected by fail2ban or similar against brute
        force attempts?
  - Recommendation: keep SSH open only if remote access is actually needed;
    disable password auth in favour of SSH keys, disable direct root login,
    and consider moving it off the default port 22 or restricting it to a
    VPN/allow-listed IP range as defense-in-depth (not a substitute for the
    above, but a useful extra layer).


PORT 8080/tcp — HTTP (Python `http.server` / SimpleHTTPServer, Python 3.12.3)
--------------------------------------------------------------------------------
What it does:
  This is Python's built-in development HTTP server (`python3 -m
  http.server`), serving files from a directory over plain HTTP. It's
  commonly used for quick local file sharing or front-end development
  testing — never intended for production use.

Security risk assessment: HIGH (in this context)
  - This is explicitly a **development/debugging tool**, not production
    software. Python's own documentation warns it "is not recommended for
    production" — it has no authentication, no HTTPS/TLS, no rate limiting,
    minimal logging, and directory-listing is often enabled by default,
    which can expose file contents to anyone who can reach the port.
  - Plain HTTP (no TLS) means any data transferred is sent unencrypted and
    can be intercepted on the network (a concern if this were exposed beyond
    localhost).
  - If this is running on a real server rather than as a genuinely temporary
    local convenience, it's a strong sign of a **forgotten debug service** —
    exactly the kind of thing regular scanning is meant to catch.
  - Recommendation: never expose this server type beyond localhost/a trusted
    dev machine. For anything resembling production file-serving, use a
    hardened web server (nginx, Apache) with TLS, authentication where
    appropriate, and directory listing explicitly disabled.


PORT 8000/tcp — Unidentified service ("http-alt?", low-confidence guess)
--------------------------------------------------------------------------------
What it does (as configured in this lab):
  A bare `nc -lk 8000` (netcat) listener — accepts raw TCP connections with
  no defined protocol, no authentication, and no logging of any kind.

Security risk assessment: HIGH — and the most concerning finding in this scan
  - Nmap could not confidently fingerprint this service at all (note the "?"
    in "http-alt?"), which is itself a red flag: legitimate, well-known
    services are usually identifiable. An unidentified open port is exactly
    the kind of finding that warrants direct investigation on the host
    (`ss -tlnp` / `netstat -tlnp` + `lsof -i` to see which process actually
    owns it) rather than being dismissed.
  - A raw netcat listener with no authentication will accept a connection
    from literally anyone who can reach it, and depending on how it's
    configured on the other end, could be used to exfiltrate data, act as an
    unauthorized backdoor, or serve as a pivot point if the host is
    compromised through another route.
  - In a real audit, an open port that no one on the team can explain should
    be treated as a potential indicator of compromise until proven otherwise
    — it's exactly the profile of a manually planted backdoor or an
    abandoned debug/test tool nobody remembered to shut down.
  - Recommendation: identify the owning process immediately, confirm it's
    intentional and understand exactly why it exists, and if not
    justified, kill the process and remove whatever started it (cron job,
    systemd service, startup script).
